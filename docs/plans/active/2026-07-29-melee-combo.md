# 무기별 콤보 액션 (근접)

> **한 작업 = 한 파일.** 끝나면 증류하고 `docs/plans/done/`으로 내린다.
> 기획 정본 = `docs/GDD.md` §6 「공격 리듬 — 콤보」(v2.2, 2026-07-29 승인).

---

## 왜

사용자 요청 — *"무기마다의 공격 리듬을 하고 무기별 액션을 만들꺼임 · 콤보액션을 만들고 싶어."*

근접 콤보는 **이미 3타로 돌고 있으나 순수 연출**이다: `_combo_index` 0→1→2→0 · 1타 방향 반전 · 3타는 `COMBO_FINISH_ARC` 1.25 / `LUNGE` 1.7 / `KICK` 2.6. **데미지·사거리·판정이 타수와 무관**하고, 세 배율이 전부 `player.gd` 코드 상수라 **무기별로 안 갈린다.** 즉 콤보를 이어갈 이유가 없다.

반면 활은 진짜 콤보다(`EquipDef.combo_*` + 호스트 `authoritative_combo`). 근접에 얹을 **검증된 경로가 이미 있다.**

🔴 **`projectb-critic` 점검이 리드의 전제 하나를 뒤집었다** — 리드는 활 콤보를 "+21%이니 선례가 있다"고 봤으나 **실측은 −3.6%(예산 중립)** 였다(궁수 cd 0.15 · 3타 사이클 0.7s에 데미지 4.5 = 6.43 DPS vs 1타 반복 6.67). 활은 뜸으로 배율을 치르고 **사거리 2배**만 얻었기에 §6을 지키며 통과했다. 근접은 사거리로 보상할 수 없으므로(도달이 최단 원거리 무기를 넘으면 역전) **새 예산 요청**이고, 사용자가 그 비용을 알고 승인했다.

## 무엇 (범위)

### 확정 범위

1. **타별 데미지 배율** — `EquipDef.combo_damage_mult`를 근접에도. 호스트가 타수를 세고 `confirm_damage`의 `combo_mult`로 들어간다(**인자 자리는 이미 있고 현재 1.0 항등**).
2. **무기마다 다른 타수** — `player.gd`의 `COMBO_MAX = 3` 하드코딩을 `CombatMath.combo_len(equip)` 유도로. 도끼 2 · 대검 3 · 창 4.
3. **마무리 타 = 광역** — 마무리 반각을 **무기별 절대값**으로 데이터에 적는다. 판정·표시가 같은 데이터에서 나온다.
4. **창 마무리 = 돌진** — 캐릭터가 앞으로 나간다(`velocity` 경유).
5. **콤보 창을 무기 데이터로** — `COMBO_GRACE_S`를 `EquipDef` 필드로 내려 활 0.8 / 근접 0.4 공존.

### 비범위

- **몸 스프라이트 애니 추가 없음**(사용자 확정) — `attack`/`attack_n` 하나를 계속 쓴다. 갈리는 것은 무기 Sprite2D 곡선뿐. **아트 비용 0.**
- **근접 사거리 배율 없음** — `combo_range_mult`는 근접에서 쓰지 않는다(`MAX_MELEE_RANGE` 130 · 「폴백 창 불변식」 여유 4px).
- **`combo_motion` 문자열 배열은 2차로 미룬다**(아래 ㉢ 참조) — 1차는 데이터(각·이징·pull·lunge)만으로 무기 성격을 가른다. 부족하면 그때 키를 만든다.

## 어떻게 (설계)

### A. 호스트 타수 카운팅 — `G_ATK` 직접 구독

**`G_ATK`는 매 스윙(헛침 포함) 브로드캐스트되고 `"cb"`를 싣는다**(`player.gd:1347`). safe 채널이라 유실이 없다. `G_HIT_REQ`(맞을 때만)로 세면 헛친 스윙을 못 세어 `min()`이 정직한 마무리 타를 깎는다 — 근접은 헛치는 것이 흔하므로 **G_ATK가 유일하게 옳은 소스**다. **새 네트워크 메시지 0개.**

- `combat_authority`가 `net_msg`로 G_ATK를 직접 구독해 `_melee_combo: Dictionary`를 갱신한다. **`_shot_combo` 선례를 그대로 물려받는다** — `peer_left` 정리 + 씬 컴포넌트라 씬마다 리셋이 공짜.
- 확정은 `authoritative_combo(주장, 이전, 경과, ...)` = `min(clamp(주장), 자기가 센 것)`. 규칙·함수를 클라와 공유한다.
- 🔴 **호스트 자신은 G_ATK를 안 받는다**(Net 루프백 없음) → 자기 콤보는 로컬 `_combo_index`를 쓴다. `player_shoot` 경로가 이미 그렇게 한다.
- 🔴 **`_combo_index` 갱신을 `play_attack_fx`의 스팸 게이트 *밖으로* 뺀다.** 지금은 게이트 안에서 `_begin_swing(combo)`이 인덱스를 소비하므로, 게이트가 한 통을 떨구면 **원격 표시 타수와 호스트 카운트가 갈라진다.** 인덱스 갱신은 애니를 재시작하지 않으므로 게이트의 목적(애니 영구 잠금·진행 중 궤적 방향 갈아엎기 방지)을 해치지 않는다.
  - 참고: 게이트 여유는 **73ms**(haste 0) / **60ms**(최대 haste)다 — `melee_fx_gate_s = max(cd×0.9 − 1/30, 0)` = 0.3267 vs 클라 송신 간격 0.4. 뜸이 붙으면 더 커진다. 드롭 위험 자체는 낮다.
- 🔴 **스키마 주석 2곳이 거짓이 된다 — 함께 고친다.** `net_schema.gd:30`과 `player.gd:1346`의 *"cb는 궤적만 정한다(판정 무관)"* → G_SHOOT `"cb"`(`:53`)처럼 *"호스트가 자기 간격으로 직접 세고 이 주장은 상한으로만 쓴다"*. 안 고치면 다음 사람이 그 주석을 근거로 "표시 전용이니 대충 다뤄도 된다"고 판단한다.

### B. 콤보 창 — `COMBO_GRACE_S`를 `EquipDef`로

지금 두 창이 갈라져 있다:

| | 식 | 값 |
|---|---|---|
| 근접(현행·로컬 전용) | `_swing_time + COMBO_WINDOW(0.55)` | **0.79~0.91s** (무기별) |
| 원거리(CombatMath·호스트 공용) | `combo_gap_s + COMBO_GRACE_S(0.8)` | **1.20~1.45s** |

⚠ **`combat_math.gd:516`의 주석 "전사는 0.4 + 0.55 = 0.95s"는 이미 틀렸다** — 코드는 클릭 시점부터 `swing_time + 0.55`를 재므로 0.79~0.91s다. 두 창을 "같은 0.95s로 맞춰 뒀다"는 07-27의 근거가 실제로는 성립하지 않았고 최대 160ms 어긋나 있었다. **이 주석도 같이 고친다.**

정본은 **CombatMath**다(이유 셋): ⑴ 뜸이 창에 들어갈 자리가 `_swing_time + 0.55`에는 없다 — 뜸을 0.4로 조이면 정직하게 낸 사람이 창을 넘긴다 ⑵ 호스트가 같은 함수를 지나야 한다(§3) ⑶ 하한이 필요하다(지금 근접엔 없다 — 없으면 스팸 클라가 쿨다운만 지키며 마무리 타를 상시 낸다).

→ `COMBO_GRACE_S` 상수를 `EquipDef.combo_grace` 필드로 내린다. **활 0.8 / 근접 0.4**. 근접 창 = `(cd + 뜸) × haste_scale + 0.4` = 0.80~1.05s로 현행과 비슷해진다. 상수 하나를 근접·활이 다투는 갈라짐 축이 사라진다.

🔴 **딸려오는 하한 — 여유가 최악 26.7ms다.** `combo_min_gap_s = (cd × 0.9 + max(0, 뜸 − 0.2)) × haste_scale`:

```
haste 0,   뜸 0    : 클라 400ms vs 하한 360ms → 여유  40.0ms
haste 0.5, 뜸 0    : 클라 267ms vs 하한 240ms → 여유  26.7ms  ← 최악
haste 0,   뜸 0.25 : 클라 650ms vs 하한 410ms → 여유 240.0ms
```

스로틀 천장과 **정확히 같은 양**이고, 넘으면 `advance_combo`가 0을 돌려 **콤보가 리셋된다**(거부가 아니라 리셋 = 계약). 증상 = "가끔 처음부터 다시 센다". ⚠ **스로틀(`melee_throttle_gap_s`)이 이걸 못 덮는다** — 그쪽은 `G_HIT_REQ`(판정) 간격을 겨누고 콤보는 `G_ATK`(클릭) 간격이다. **수용하고 `TUNING`에 기록한다**(부호가 안전한 쪽이고, 최대 haste에서만 좁다).

### C. 마무리 각 — 절대값이 세 결함을 한 번에 닫는다

배율(`COMBO_FINISH_ARC` 1.25)로는 **원리적으로 못 막는다.** 포화 문턱 = `(π − ε) ÷ swing_arc`:

| 무기 | `swing_arc` | 포화 문턱 | 1.25 적용 시 |
|---|---|---|---|
| 파쇄 도끼 | 2.8 (160.4°) | **1.122** | ❌ 3.5 → **전방위** |
| 철 대검 | 2.4 (137.5°) | 1.309 | ✅ 3.0 (171.9°) |
| 낡은 대검 | 1.9 (108.9°) | 1.653 | ✅ 2.375 (136.1°) |
| 장창 | 0.3 (17.2°) | 10.47 | ✅ 0.375 (21.5°) |

→ **`EquipDef.combo_finish_arc`(절대 목표 반각)** + `melee_half_angle`이 `min(목표, MELEE_FULL_ARC − ε − 여유)`로 자른다. 한 처방이 셋을 덮는다:

1. **포화 차단** — 넓은 무기가 조용히 전방위가 되지 않는다.
2. 🔴 **도끼 표시 span이 오늘 이미 TAU를 넘는 것도 닫힌다** — `arc 2.8 × 1.25`를 양쪽으로 쓰면 span 7.0 rad = **401°**다. 즉 도끼 마무리는 **지금도 한 바퀴 넘게 휘두르고 있고** 「철 대검 = 회전 베기」와 화면에서 구별되지 않는다. 어깨걸치기 상한(`cap`)은 기본 span을 줄이지 않는다.
3. **표시 > 판정 여유를 같은 자리에서 준다** — 판정 각과 표시 각을 **따로** 적어 표시가 항상 조금 넓다(§D).

### D. 표시 > 판정 여유 — A-2 관측 경로 보존

지금 A-2(궤적 결손)를 눈으로 검사할 수 있는 이유는 표시(×1.25) > 판정(×1.0)이라 *"판정 안인데 궤적이 안 지나간 자리"* 가 보이기 때문이다. **표시 = 판정이 되면 비교 대상이 사라진다.**

→ 마무리 타의 **판정 각 < 표시 각**을 데이터로 강제한다(예: 판정 목표 반각 + 표시 여유). `test_combat_math_auto`가 `data/equipment` 전수로 `판정 반각 < 표시 반각`을 단정한다.

⚠ **착수 전 실기 1건(A-2, 5분)** — `?host&debug=1` → F1 「전부 열기」 → 시험장 → **철 대검**으로 부채꼴 **가장자리** 허수아비를 **0·1타만**. 지금 찍어 두지 않으면 마무리 타 판정이 넓어진 뒤 결함의 출처를 영구히 가릴 수 없다.

### E. 표시 규칙 — 인덱스 축을 하나로

현행 두 조건이 **서로 다른 인덱스 축**을 본다 — 반전은 절대 위치(`== 1`), 마무리는 끝(`len − 1`):

| 타수 | 반전 타 | 마무리 타 | 충돌 |
|---|---|---|---|
| **2 (도끼)** | 1 | 1 | 🔴 **동일** — 마무리가 "반전된 마무리"가 된다 |
| 3 (대검) | 1 | 2 | 없음 (현행) |
| 4 (창) | 1 | 3 | index 2가 0과 같은 방향·크기 → **두 타가 같은 궤적** |

→ 방향을 **`index % 2`**(짝수 좌→우 · 홀수 우→좌)로 바꾼다. 타수 무관하게 왕복이 유지되고 마무리 조건과 **절대 안 겹친다.**

### F. 창 돌진 — `velocity` 경유가 계약이다

🔴 **`swing_lunge`는 몸 이동이 아니다.** `_motion_lunge`의 소비처를 전량 추적했다 — **`player.gd:978`(무기 스프라이트 위치)과 `:1540`(리본 선단 거리) 둘뿐이고 `velocity`/`position`에 들어가는 곳이 0곳**이다. 그리고 창은 이미 `15 × COMBO_FINISH_LUNGE 1.7` = **25.5px**를 마무리 타에 쓴다. 사용자는 그것을 알고 **"캐릭터가 진짜로 나간다"** 를 선택했다.

- 🔴 **`velocity`를 통해 움직인다 — `position` 직접 대입 금지.** 대입하면 G_POS의 `vx/vy`가 0이라 호스트의 lead 외삽이 그 변위를 **원리적으로 못 덮고**, 그게 곧 "마무리 타 전체 무음 거부"다.
- 🔴 **각 예산이 거리를 묶는다.** 각 오차 = `asin(변위 ÷ 도달)`이고 창은 도달 80px·반각 17.2°라 **24px에서 이미 예산을 넘긴다**(`80 × sin(0.3)` = 23.6). ~~광역이 이걸 덜어 준다 — 마무리 반각 0.6이면 예산 45px로 벌어져 지연 슬랙 18px를 빼도 대시 27px가 들어간다.~~
  - 🔴 **이 커플링은 구현 중에 끊겼다 — 위 서술은 더 이상 참이 아니다** (리뷰 I-3·A-1, 2026-07-29). 창 마무리 각을 주면 `thrust`가 `_swing_to = 0`이라 **칼이 한쪽만 지나는데 판정은 양쪽**이 되어 「표시 ⊇ 판정」이 공간 축에서 깨진다(그 띠가 각의 정확히 그 배수로 벌어진다). 그래서 창은 `combo_finish_arc`를 **받지 않기로** 했고, 그 결과 예산이 base 0.3 기준 **23.64px**로 돌아가 대시 20px가 84.6%를 먹는다 — **잔여 3.64px**(설계가 상정한 지연 슬랙 18px보다 작다).
  - ⚠ **확정 고장은 아니다:** `mob_lag_slack_px`가 **각에만** 더해져 편도 100ms에서 0.227 rad(콘의 76%)를 보태고, 대시가 균일 속도라 `net_anchor_lead` 외삽이 거의 정확히 덮으며, 각은 **두 apex 중 하나만** 통과하면 된다. **판정은 D-6 실기가 낸다** — 그것이 이 작업의 최우선 확인 항목이 된 이유다.
- 🔴 **대시는 판정 순간까지 진행 중이어야 한다.** 판정 전에 멈추면 velocity가 0이 되어 `net_anchor_lead == net_anchor`가 되고, 그러면 오차 = 대시 거리 **전체**가 남는다(최악). 스윕 구간에 배치하고 판정 직후 감속한다.
- ⚠ **`LAG_MAX_LEAD_DIST`(115) 재유도 + clamp 3곳**(`_max_move_speed` · 원격 속도 clamp · 원격 변위 clamp) — `roll_dist` 선례를 그대로 따른다. `projectb-rules` §2 게이트 대상이고 **netreview 필수**다.

### G. 데이터 트립와이어 (`test_combat_math_auto`)

`combo_len`이 세 배열의 최대 크기라, 근접 `.tres`에 `combo_range_mult`를 실수로 넣으면 **사거리는 안 바뀌고 타수와 마무리 타 위치만 조용히 옮겨간다**(그 배열을 읽는 곳이 근접 경로에 없다). `MAX_MELEE_RANGE`·「폴백 창」 트립와이어 어느 것도 이 축을 안 본다.

- **`motion_type` ∈ {"", swing, thrust}인 무기는 `combo_range_mult`가 비어 있어야 한다** — 전수 단정.
- **비감소 단정을 근접 `combo_damage_mult`로 확장** — 뒤 타가 앞 타보다 작으면 안 된다.
- **판정 반각 < 표시 반각** — 전수(§D).
- **사이클 DPS 비 ≤ 1.3** — GDD §6 예산표를 코드가 지킨다. 🔴 `clamped == raw` 관용구로 쓴다(상한 값을 테스트에 복제하지 않는다).
- ⚠ 단정 대상 상수·함수는 **`combat_math.gd`에** 둔다 — `player.gd`는 씬 글루라 `-s` preload가 안 돼 겨눌 수 없다(리뷰 J-1·J-2).

### H. 🔵 미루는 것
