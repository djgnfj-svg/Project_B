# GDD 작성·수정 규율

**이 문서는 리드(메인 세션)가 쓴다.** 기획은 사용자와의 대화가 본질이라 서브에이전트에 위임하지 않는다 — 위임하면 대화가 한 겹 끊기고, 빈칸을 에이전트 상상으로 채우게 된다.

**파이프라인 (2026-07-26 확정):**

```
① 브레인스토밍  — 메인 세션에서 사용자와 대화로 정한다 (리드)
② 점검          — projectb-critic 에이전트 (방법론 = projectb-plancheck)
③ 문서화        — 이 스킬을 읽고 리드가 GDD에 반영 (🔒 사용자 승인 후)
④ 구현          — projectb-dev
```

②를 건너뛰지 마라. 정한 직후엔 모순이 안 보인다 — 특히 §과 § **사이**의 충돌은 만든 사람이 구조적으로 못 본다.

## 🔒 최우선 규칙 — GDD 수정은 승인제

`docs/GDD.md`는 프로젝트의 기획 정본이다. **사용자 승인 없이 절대 고치지 않는다.**

1. **먼저 읽어라.** `docs/GDD.md` 현재 상태 + **구현이 어디까지 갔는지**(`CLAUDE.md` 상태 줄 · `docs/CHANGELOG.md`). 기획이 **이미 구현된 것을 "앞으로 할 것"처럼** 쓰면 그 자체가 새 모순이다.
2. **바꾸기 전에 제안하라.** 어떤 장(§)을 무엇에서 무엇으로 바꿀지 **실제 들어갈 문구 그대로** 보여준다 — 한 문장 요약이 아니다.
3. **승인을 받아라.** 사용자가 명시적으로 동의하면 그때 Edit/Write 한다. (`.claude/settings.json` 권한 규칙이 매 편집에 확인을 요구하지만, **규칙에 기대지 말고 먼저 물어라** — 규칙은 안전망이지 절차가 아니다.)
4. **수정하면 이력을 남겨라.** 문서 맨 아래 「변경 이력」에 날짜·변경·사유 한 줄, 상단 「최종 수정」 갱신.

왜: 기획이 조용히 바뀌면 dev가 옛 합의로 만든다. 진실원은 **모두가 믿을 수 있어야** 진실원이다 — 그래서 바뀔 때 사용자가 안다.

## 🔴 미러 규약 — 한쪽만 고치면 갈라진다

- **플랫폼·엔진·렌더러·아트 스타일**은 `CLAUDE.md` 「정체」 줄과 GDD §3이 **미러**다. 둘을 나란히 열어 놓고 고친다.
- **미정 수치**는 GDD §11(열린 질문)과 `docs/TUNING.md`가 짝이다 — 실기로 조일 값은 GDD에 확정 수치로 박지 않는다.
- **구현 이력**은 GDD가 아니라 `docs/CHANGELOG.md`가 정본이다. GDD는 "무엇을 만들 것인가"만 담는다(했다/안 했다를 쓰기 시작하면 두 번째 진실원이 된다).

🔵 **현재 계류 중인 미러 부채 (2026-07-26 — 처리하면 이 줄을 지운다):**
1. **캐릭터 크기·기준 해상도가 구현에는 있는데 GDD에는 없다.** GDD §9(`:225`)가 "기준 해상도 · 팔레트 · 캐릭터 크기: _TBD_"에서 멈춰 있고 `16px`·`32px`·`640×360` 문자열이 **0건**이다. 현행 구현 = **캐릭터 32px · 640×360 · 카메라 줌 1.5**(줌은 2026-08-02 실기 확정 — 그 전엔 1.0이었다). 🔴 **다만 이 값은 확정으로 적지 마라 — 07-26에 16px로 갔다가 07-27에 32px로 되돌아왔고, 줌도 07-27에 「1.0 유지 확정」이던 것이 08-02에 1.5로 뒤집혔다**(둘 다 실기 플레이로 판단이 뒤집혔다). GDD에 넣으려면 사용자에게 "이제 확정인가"를 먼저 물어라. 그 전까지는 TBD가 오히려 정직한 상태다. ⚠ CLAUDE.md가 §3과 **미러라고 선언한 범위**(플랫폼·엔진 4.7.1·렌더러 Compatibility·아트 스타일)는 양쪽이 **일치**한다 — 즉 미러가 깨진 게 아니라 **새로 확정된 사실이 GDD로 안 내려간 것**이다.
2. 사용자가 방향으로 언급한 **"캐릭터 1개 + 무기가 직업"** 은 미착수다 — `job_id`가 하위 직업 계열의 뿌리라 **GDD 변경이 선행**이다.

✅ **해소됨: "아트 규격 정본이 없다"** — 정본은 `projectb-art` 에이전트 파일이다(캔버스·시트·애니 프레임/fps·팔레트 현황·FX 미러가 실측으로 박혀 있다). 현행 = **캐릭터 32px**(2026-07-27 — 07-26의 16px를 되돌린 값). 이 항목이 1번과 묶여 있어 1번 처리를 미루던 이유였으니, **이제 1번은 독립적으로 처리할 수 있다** — 단 위 1번의 🔴 경고(확정 여부를 먼저 묻기)를 지켜라.

## 기획 방식

- **질문으로 좁혀라.** 빈칸을 상상으로 채우지 마라. 핵심 루프·성장·범위 같은 결정은 사용자 것이다. 한 번에 2~3개씩 **구체적으로** 물어라 — 추상적 "어떤 게임 원해?"가 아니라 "성장은 A: 레벨업 / B: 장비 강화 / C: 스킬 해금 중 뭐에 가까워?".
- **핵심 루프부터.** GDD의 뼈대는 §4다. 이게 서면 나머지(메커니즘·콘텐츠·시스템)가 거기 매달린다. 루프가 흐릿하면 그것부터 세운다.
- **범위를 지켜라.** §10 비범위를 적극 채워라 — "안 하는 것"을 정하는 게 "하는 것"만큼 중요하다. 기능 폭주를 문서로 막는다. ⚠ 해커톤 마감(2026-08-10)까지 **약 2주**다.
- **열린 질문을 쌓아라.** 지금 못 정하는 건 §11에 남기고 넘어간다. 미정을 억지로 확정하지 마라.
- **손맛·수치는 확정하지 마라.** 판정 반경·데미지 밸런스는 "사용자가 플레이하며 조인다"로 남긴다(`projectb-verify`와 같은 철학).
- **구현이 이미 굳힌 것은 열린 선택인 척하지 마라.** 코드로 배포된 결정(예: 하위 직업 조립 축·P2P 직결)은 바꾸려면 재작업 비용이 든다 — 바꾸자는 제안이면 그 비용을 함께 적는다.

## 산출물 형식

```
## 기획 논의: [주제]
- 지금 GDD 상태: [해당 §의 현재 내용]
- 점검 결과 반영: [projectb-critic이 잡은 것 중 무엇을 어떻게 해소했나 / 점검 안 했으면 "먼저 critic에 넘길까요?"]
- 정할 것: [질문 2~3개 — 선택지 제시]
- 제안 변경안:
    §N [장 이름]: "[들어갈 실제 문구]"
- 미러 확인: [CLAUDE.md 「정체」·TUNING·CHANGELOG 중 같이 고칠 것 / 없으면 "없음"]
- 승인 요청: "이대로 GDD에 반영할까요?"
```

승인 전에는 **문서를 건드리지 않는다.**

## 반영 후

- GDD가 바뀌어 구현이 필요해지면 `projectb-dev`에 넘긴다(큰 시스템이면 dev가 설계 스케치부터 낸다).
- 아키텍처 규칙(모듈·EventBus·데이터 주도)이 기획에 걸리면 `projectb-rules`를 참고하되, 기획 결정 자체는 사용자와 정한다.
- 🔴 **기획 변경이 코드 계약을 건드리면** `projectb-rules` §2 게이트·§3 계약도 같이 갱신해야 하는지 본다 — 예: 화력 예산(GDD §6)을 바꾸면 스탯 상한 검증의 기준선이 움직인다.
